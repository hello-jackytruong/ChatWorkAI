## Minimal proposed contracts (plan recommendations, not existing routes)

Recommend **same authorized conversation read access**, rather than a new permission field/role. Stored originals already belong to workspace message history; checklist does not request an administrator-only archive. For sessions/mobile, use the actual Inbox/conversation read ACL, including assigned/team scope; workspace tokens use `inbox` scope and existing workspace-level semantics. A stricter role is a material product choice and requires closing ordinary list/detail/realtime/media bypasses anyway. No permission schema expansion is necessary for this section.

Place public procedures in the existing Zalo feature, but create their own `workspaceTokenAuthAPIForScope("inbox")` base instead of inheriting that feature's existing `channels` base (`api/public.ts:26`; `api/operations.ts:24`). They act on conversation history. Session actions/private handlers resolve equivalent scope then call the same business method under `packages/business/src/zalo-account/`.

Suggested routes and return shapes:

- `GET /v1/zalo-accounts/{accountId}/conversations/{conversationId}/messages/{messageId}/saved-content`, procedure `getSavedMessageContent`; require `createdAt` for shard routing. Bind workspace/account/Inbox/conversation/message and `channel === zaloAccount` before returning anything. Response is explicit safe text, stored attachment descriptors, original availability (`stored` / `notCaptured`), provider recall timestamp (nullable), observed timestamp, actor (nullable), and recall state. A missing original with known tombstone is a successful `notCaptured` result, not invented empty original text.
- `GET /v1/zalo-accounts/{accountId}/conversations/{conversationId}/messages/{messageId}/saved-content/attachments/{attachmentId}`, procedure `getSavedMessageAttachment`; same checks including attachment ownership and stored-key status; return short-lived signed URL + safe filename/MIME/size. No storage key, provider URL, arbitrary redirect, media proxy retry, or re-fetch from Zalo. If missing/not yet stored, return explicit unavailable state; don't pretend it was archived. Existing key alone is not proof object exists.
- `POST .../messages/{messageId}/recall`, procedure `recallMessage`; body includes stable commandId and createdAt. Server resolves provider msgId/cliMsgId, self ownership, account/thread; never takes arbitrary raw UID/IDs from caller. Return command status, never claim recall based on enqueue alone.
- `POST .../messages/{messageId}/delete-on-zalo`, procedure `deleteMessageOnZalo`; explicit self-side semantics (`onlyMe: true` internally). This does not mean recall or delete internal originals. If later exposing group moderation delete-for-everyone, require an explicit distinct scope and live permission proof; never inherit SDK default false.
- `POST /v1/zalo-accounts/{accountId}/conversations/{conversationId}/delete-on-zalo`, procedure `deleteChatOnZalo`; body references an exact persisted last-message identity/createdAt plus commandId; server resolves immutable backward deletion boundary. Own-side provider conversation clear only; preserve ChatbotX Conversation, ContactInbox, Messages, attachments, receipts and reactions. Never route to workspace/conversation purge.
- If section's “internal delete” is implemented as local hide, use a dedicated operation `hideMessageLocally` and explicit label “Hide in ChatbotX”; no provider call, no recall timestamp/actor, no attachment purge. A shared `deletedAt` alone cannot distinguish it. Preserve generic Zalo delete rejection to prevent ambiguous legacy clients.

Every public route needs `.errors(...)`, explicit `.output(...)`, and mcpSpec destructive confirmation for provider delete/recall/clear even though POST. Distinguish pending/applied/failed/unknown and immutable command target, avoid blind retries after timeout. Reuse fenced gateway command transport/state machinery, not arbitrary SDK method execution. New transport union variants and gateway/pool/runtime methods are required: current `packages/sdk/src/lib/zalo-account.ts:486` and `apps/zalo-account-gateway/src/transport/command-executor.ts:116,229-294` have no native undo/delete command.

Accepted controller decisions: keep existing conversation read ACL and `inbox` token scope; **group delete-for-everyone moderation is out of scope**. `deleteMessage` always passes onlyMe=true, undo is separate, and deleteChat changes no local message rows. Best-effort original-view/link-issued auditing is sufficient; do not imply actual-byte download audit.

Expiry/deletion gates need explicit parity in the plan. Existing generic delete uses `workspaceActionClient` (`delete-message.action.ts:93`), which blocks owner quota/trial and scheduled workspace deletion (`lib/safe-action.ts:194-218`). `workspaceActionClientAllowExpired` at 134-191 still proves session, membership, host tenancy and audit actor but skips those extra gates: new read/delete actions should use it and explicitly preserve scheduled-deletion protection where required, rather than accidentally bypass that guard. Public+private oRPC already permit reads/DELETE past expiry (`middlewares/auth.ts:86-98`; `middlewares/workspace-token-auth.ts:250-272`). A POST native delete/clear/recall is considered mutation unless its exact path is added to the **owner-quota-only** allowlist at `lib/workspace/authorize-workspace-access.ts:215-244`; this does not belong in the read-only-token POST allowlist. Decide which destructive native deletion actions remain usable in expired read/delete mode, then pin session/token parity and scheduled-deletion behavior in RED tests. Recommended: deletion/recall/clear stay available with normal ACL+live provider restrictions, read-only tokens still cannot invoke any of them. Existing disconnect/cancel-style POST exceptions in that file demonstrate the narrow pattern. Avoid changing the gate for other channel operations.

UI: recalled Zalo bubble and conversation preview show “Đã thu hồi trên Zalo”; explicit “Xem nội dung đã lưu” opens on-demand dialog, shows text/file availability and timestamps, unknown actor remains unknown. Keep quote/reply messages independent. Clear dialog/query data on close, conversation/account/workspace change; avoid persistent global/store caching of originals. Recall on own messages only with complete stored provider refs, delete-own-side distinct, clear-chat in conversation menu with boundary and scope explanation. Do not reuse comment delete confirmation. Add all keys to all 20 locale files. Ordinary non-Zalo channels and generic deleted labels remain unchanged.

## Media/access boundary and audit

`apps/builder/src/features/attachments/utils.ts:16-37` can reconstruct storage URL from originPath if URL absent. Therefore deny/redact must explicitly remove keys or use null URL; undefined URL is not a denial. Original API must never pass untrusted `originPath` into this normal renderer. A small saved-content attachment renderer should use only the authorized URL response.

`apps/builder/src/app/media/media-proxy.ts:48-85` verifies a bearer media token and workspace servability, not user membership/assignment; `app/media/attachment/[token]/route.ts:72-114` finds attachment and signs/redirects without parent deletion check. This existing proxy is not the new archive authorization gate. Do not add an unauthenticated fallback or issue these tokens for saved originals. For Zalo, stored keys currently presign directly because `HYDRATION_CHANNELS` at `business/src/media/resolve-media-url.ts:11-15` excludes Zalo. Do not expand this shared media pipeline or change other channels merely to implement recall review.

For access-controlled review, ordinary recalled-Zalo list/detail/preview/realtime projections must omit original text, nested raw payload content, provider URLs, object keys and signed URLs; expose only safe marker/identity/availability metadata. Keep stored DB data intact. Add Zalo-only branch before attachment signing to avoid minting bypass URLs. Review exact raw/detail entry points and existing late message events. Existing previously issued signed URLs cannot be retroactively revoked; their TTL and storage access policy bound that exposure. A plan must not promise immediate revocation without a separate storage design. Read-only research did not verify tenant storage ACL settings.

Use existing audit infrastructure for successful review and attachment URL issuance/provider operations: `packages/business/src/audit/service.ts:18-68` and `audit/dispatcher.ts:32-61`. Record action, workspace/account/conversation/message/attachment IDs, commandId, outcome and caller source; no original text, cookies, URLs, auth tokens, raw payload. Workspace-token actor context attributes to owner (`audit/service.ts:23-29`); retain request token identity only through an existing safe identifier if available. This queue audit swallows enqueue failure, so document it as **best effort**, not a compliance-grade durable access ledger. A strict fail-closed ledger is larger scope. Download audit records URL issuance, not proven completion of bytes downloaded.
