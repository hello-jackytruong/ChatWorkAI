## Findings with evidence

- `packages/business/src/zalo-account/message-lifecycle.service.ts:35` validates account/inbox and group policy. At `:85`/`:103` it requires existing ContactInbox/conversation BEFORE undo bookkeeping; therefore an undo before first DM/contact provisioning disappears without a tombstone. At `:139` only group undo is durable. At `:150` it invokes shared delete, then `:155` clears tracking detail. Missing message retries cannot repair an undo never recorded because its conversation was absent.
- Shared `packages/database/src/sharding/message/repository/sharded-message-repository.ts:1004` is unsafe for this feature: source lookup with hinted shard then all-time fallback (`:1052`), followed by parent **and children** soft-delete (`:1095`, `:1118`). It catches per-shard lookup/update failures and returns partial results (`:1044`, `:1130`). Do not change this shared behavior for production channels; introduce an explicitly scoped exact-one ZA mutation path. `deleteById` at `:1152` targets one tuple but catches failures and lacks full conversation/contact/provider guards, so is insufficient as-is for authoritative recall projection.
- `packages/database/src/repositories/integration-zalo-account/message-state-repository.ts:87` checks undone only for groups. `:103` has a suitable full-provider-target advisory lock. `:250` persists a group undo, but `:276`/`:288` sets discardedAt and erases payload. `:296` physically deletes receipt/reaction detail. Remove this clear from recall. Existing rows already represent bounded per-member receipts and latest actor/key reaction state, not an immutable reaction-event log; keep that bounded model and its documented 90-day retention rather than inventing an unbounded event log.
- `packages/database/src/schema/zalo-account-message-identity.ts:22` is a **group persistence outbox**, not a general lifecycle ledger: required groupId and policy epochs (`:39`, `:46`), required placeholder Message pointer (`:48`), unique workspace/account/group/provider target (`:65`). Reusing it for DM would unnecessarily widen group recovery and admission contracts.
- `packages/database/src/repositories/integration-zalo-account/group-inbox-repository.ts:119` correctly commits stable identity before the Message shard. Its second transaction locks identity (`:152`) and rejects undone/discarded/published/missing-payload rows (`:158`). `:207` creates canonical Message+attachments with stable identity; `:256` erases replay payload after publication. This payload is not a retained-original archive. Keep the group outbox schema, but a narrow logic change is unavoidable if late originals must be retained: recall cannot discard/erase the pending original, and a late original must be persisted in recalled form without normal automation. `packages/business/src/zalo-account/group-inbox.service.ts:75` currently publishes and invokes onMessage for any isNew result; add an explicit recalled outcome there, not a global change to all group messages.
- DM integration preserves provider/client/thread/sender/time/quote in `integrations/zalo-account/src/message.ts:130`–`:178`; attachments enter the common pipeline. DM storage is `apps/worker/src/integration/handlers/received-message.ts:1320` (message identity/build), `:1404` (upsert), `:1498` (persistence), `:1554` (new-message side effects). Add a ZA-only lifecycle seam immediately around canonical persistence before broadcast/automation, leaving other integrations on the existing path. Merely checking before or after upsert without serialization leaves a recall/message race.
- Message is sharded with no main-store FK (`packages/database/src/schema/message.ts:63`). Exact pointer includes both id and createdAt; attachment linkage needs that timestamp too. `findById(...primaryAndFailOnError:true)` at sharded repository `:1842` provides authoritative reads with exact tuple/workspace/conversation filters. `findBySourceId` at `:2260` requires sinceTime, fans out using Promise.all, reads replicas, and catches failures as null. - `packages/business/src/zalo-account/message-state.service.ts:65` allows max 50 provider IDs and validates account/group or direct ContactInbox binding (`:89`–`:113`); its service does not resolve member ACL itself. Reuse route resolution, but original view/download must receive actual conversation access scope from the caller. Do not treat account ownership alone as permission to view an assigned/restricted conversation.
- Provider normalization `apps/zalo-account-gateway/src/runtime/provider-thread-event.ts:44` distinguishes provider/observed timestamps; undo currently retains only globalMsgId (`:53`). Installed `zca-js/dist/models/Undo.d.ts:8` includes uidFrom, ts, actionId, but this does not prove uidFrom is the actor in every delete/recall variant. ## Minimal durable design

Use a narrow new `ZaloAccountMessageRecall` ledger rather than generalizing the group outbox. Unique key: workspaceId + accountId + threadType enum + provider threadId + providerMessageId. Optional groupId references local group for purge/admission. Store providerRecalledAt **nullable** (observed time is not provider time), first receivedAt, optional provider actor, nullable Message id/createdAt and optional local conversation/contactInbox pointers. Track pending/applied projection via nullable appliedAt (plus bounded retry scheduling fields only if needed). No copied text, raw SDK packet, credentials, or attachment bodies. Canonical Message+Attachment remain original authority.

Record admissible recall before resolving optional direct contact/conversation. Preserve account/workspace/inbox validation and group policy epoch admission. Unknown direct thread may receive a ledger tombstone, but do not create a customer/contact or fake original solely from recall. UI/API can report recall-only, original-never-observed state using ledger; if a timeline placeholder is required, identify it explicitly as a placeholder and reconcile late originals to the same identity. Never manufacture original content or provider actor.

Use the same full-target advisory key for recall and ZA DM/group canonical persistence. Under bounded main-store transaction admission/lock, read/write ledger and store/mutate exact canonical shard tuple; there is no cross-store transaction, so main ledger is durable intent and projection must be idempotently repairable. No HTTP/storage/provider calls under that transaction. Prefer primary reads and throw on shard unavailability; do not mark applied or emit success on partial write. A crash after shard write but before main commit must be safe to repeat. A crash after durable intent but before shard write must leave pending repair. Applied projection must use atomic JSON overlay or a dedicated exact update, not overwrite stale contentAttributes or clear text/attachments.

For new messages, bind known pointer once and reconcile pending recall before normal broadcast/side effects. For group, preserve existing stable group identity/payload recovery; replace the discard-on-recall branch with a retained/recalled persistence outcome. Legacy undone group identities without originals cannot regain erased content unless a late provider message supplies it. Existing Message originals remain recoverable since current delete is soft. Keep tombstones for as long as import/replay can rediscover provider IDs; 90-day receipt retention must not expire recall protection.

Existing old DM rows need a bounded fallback locator, because no durable DM pointer exists. Resolve target within the validated conversation/contactInbox; walk bounded shard ranges sequentially with a resumable cursor and primary reads. Recent-range lookup may be a first attempt, but **90 days is not a correctness cutoff** for old original tracking. A failed shard is retryable/unavailable, not missing. If scan budget expires, report pending/unresolved and continue next recovery tick; never fan out every historical shard or disclose another conversation's same provider ID. New direct ingress/outbound sends should bind pointer as part of their ZA seam; use existing applied SendAttempt pointers for own sends and group identity pointers where available.

No recall path deletes attachments, rewrites stored paths, or calls object delete. Saved originals can only promise downloads for bytes already stored; current inbound URL-only attachments are not proof of durable S3 bytes (P0 §2 dependency). Expose saved/unavailable state rather than attempting arbitrary provider fetch during original-view. Receipt/reaction rows retained at recall; decide whether later events update latest aggregates under existing timestamp ordering or are ignored, but neither option may restore a message. Do not add a full event journal under the phrase “history.”

ZaloCRM `/Volumes/DevSSD/Work/GitHub/ZaloCRM/backend/src/shared/zalo-operations.ts:390` confirms nested delete destination and explicit onlyMe; `:405` confirms undo object signature; `:420`–`:434` retries known provider error 112 using delays 3/5/7 seconds. This is reference anecdote, not proof of safe retries or a reason to sleep gateway workers. Do not copy automatic retries after unknown timeout. No deleteChat wrapper exists in that reference file.

Create a separate compact native-operation attempt ledger (operation enum undo/deleteMessage/deleteChat; same scoped target, stable commandId and immutable request hash; provider boundary; pending/dispatched/applied/failed/unknown; sanitized provider status/error). Enqueue recovery may recover only work proven not dispatched. Known 112 can be presented retryable with a new explicit attempt only after live evidence, never blind retry of ambiguous dispatch.

Native delete-my-side and internal hide require distinct metadata/labels and must not create a provider-recall tombstone. Native undo confirmation and incoming undo converge on same recall ledger. Native deleteChat records boundary/attempt without deleting canonical originals. Internal ChatbotX hide remains separate exact local marker; do not reinterpret generic delete as unsend. Full P0 §3 includes all three operations, but enablement stays capability/proof gated until redacted live DM/group fixtures verify statuses, permissions, receive events, time/ownership restrictions and onlyMe behavior.

## Retention, purge, and migration

- Keep 90-day bounded detail purge in `message-state-repository.ts` and worker `apps/worker/src/schedule/handlers/purge-zalo-message-state.ts:4`–`:19` (10 batches, 40-second deadline, 500 rows/table per transaction). Recall must not call clearTarget; no new unbounded history table.
- New recall and native-attempt tables need leading workspace/account/group indexes, full target unique indexes, partial pending recovery indexes ordered by due/update time + id; no FK to sharded Message. Register schema/types/relations including both import and spread. Use real SQL defaults or explicit insert fields.
- Register both high-volume tables in `packages/database/src/repositories/workspace-purge/tables.ts:1`, child before account/group/workspace parents. Reuse purge guard for all writes and bounded recovery; disabled/deleted workspace cannot recreate ledger rows.
- Recall is independent from intentional contact/workspace destruction. `packages/business/src/message-cleanup/service.ts:210` deletes canonical Message+Attachment for removed ContactInbox and calls storage deletion at `:276`; do not accidentally exempt recalled content from an explicitly authorized data deletion. Conversely, a recall alone must never enqueue MessageCleanup. Add narrow contactInbox cleanup for new ledger pointers if needed, or avoid parent FKs that create unbounded cascade scans; do not leave bodies/secret URLs in new ledgers.
- Generate and inspect additive migration, do not run db:migrate. Old group undoneAt backfill to recall ledger must be bounded and cannot recover erased pending payload or erased receipt/reaction history. Do not infer provider event time from system generated timestamps where provenance is absent. This is a rollout limitation, not a reason for fabricated history.

## Concerns / limits

The smallest complete scope still needs a schema migration and a small ZA-only seam in the shared receive file. Group outbox logic cannot be literally unchanged while both tombstoning late originals and retaining them for authorized review. Current inbound media can be provider-URL-only, so full byte recovery cannot be promised without P0 §2. Static zca-js and ZaloCRM inspection establish invocation shapes, not live permissions/status/event semantics. Existing erased receipt/reaction rows and erased pending payloads cannot be reconstructed from this code.
