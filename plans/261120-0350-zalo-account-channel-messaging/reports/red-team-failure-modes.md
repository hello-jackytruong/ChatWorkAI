# Red-team failure modes: items 5–9

This review covers the transport, registration, direct messaging, group-control, and native-label plans (items 5–9), the two research reports, `docs/zalo-account.md`, and the current gateway, event-bus, worker, lifecycle, purge, and schema seams. It is limited to failure behavior and operations. No product code or plan file was changed, and no install, build, typecheck, test, or lint command was run.

The amendments below are intentionally small: each asks the implementation phase to make an invariant explicit and test the failure boundary. The sequential low-RAM constraint remains in force.

## Findings

### 1. High — A shared consumer group cannot provide the planned gateway broadcast

- **Plan location:** `phase-05-fenced-gateway-transport.md:21,35-36,49`; the contract says untargeted start/reconnect commands are observed by all active replicas, while the tests require two replicas to observe the broadcast and exactly one owner.
- **Evidence:** The existing Redis Streams primitive uses one `XREADGROUP` assignment per entry (`packages/event-bus/src/event-bus.ts:203-215`), and `cloneForGroup` only creates a different consumer group when explicitly configured (`packages/event-bus/src/event-bus.ts:233-237`). The current transport is not yet a fan-out implementation.
- **Concrete failure:** If all gateway replicas consume the same group, only one replica sees an untargeted command. If each replica is given an independent group without a receipt/fence protocol, every replica can start the same provider session, causing duplicate sockets or provider kicks. A crash of the one assigned consumer can also delay QR/connect work until reclaim.
- **Minimal plan amendment:** Specify the fan-out topology before implementation: one durable consumer group per gateway replica (or an equivalent explicit fan-out stream), with a deterministic command ID and per-replica receipt/reclaim; keep ownership acquisition/fence validation as the single execution gate. Add a two-replica test covering both observation, one owner, consumer crash, and reclaimed delivery.

### 2. High — Process restart has no durable desired-state reconciliation

- **Plan location:** `phase-05-fenced-gateway-transport.md:39,68,72-74`; `plan.md:99-100`; `phase-06-channel-registration-and-inbox.md:24,38`. The success criteria require restart recovery and idempotent stable IDs, but do not name a startup recovery mechanism.
- **Evidence:** Gateway startup creates a new empty pool (`apps/zalo-account-gateway/src/main.ts:21-37`); the pool’s runtime, epoch, and cancellation state are in memory (`apps/zalo-account-gateway/src/runtime/zalo-account-pool.ts:25-31`). No startup scan or durable reconnect supervisor is present. Lease expiry only releases ownership; it does not recreate a socket.
- **Concrete failure:** A crash after the provider socket connects, or after a command is appended but before its lifecycle event is appended, leaves the durable account/connection state apparently active while the new process has no runtime. Pending stream entries may be reclaimed, but an already-acknowledged command or an event lost before append cannot recreate the desired runtime. The account silently stays disconnected until an operator or UI action happens.
- **Minimal plan amendment:** Add a bounded startup reconciliation step: enumerate durable accounts whose policy is active, acquire the current fence, and issue one idempotent reconnect per account; reconcile pending command/session state before declaring readiness. Define manual-disconnect as a durable “do not resurrect” state. Add crash-point tests at lease acquisition, SDK start, socket connected, and before event append, including restart with two replicas.

### 3. High — Stale events can lose tenant scope at the worker boundary

- **Plan location:** `phase-05-fenced-gateway-transport.md:19-24,48`; `phase-06-channel-registration-and-inbox.md:24,38`; `phase-07-direct-messaging.md:27-31,52`; `plan.md:99,104`.
- **Evidence:** The current local runtime check only verifies local active/generation/lease state (`apps/zalo-account-gateway/src/runtime/zalo-account-runtime.ts:450-460`). The generic incoming-message job carries only `integrationType`, `integrationIdentifier`, and `payload` (`packages/worker-config/src/queues/integration/index.ts:132-139`). Workspace resolution is explicitly best-effort and returns `undefined` on lookup failure (`apps/worker/src/lib/resolve-workspace-id.ts:103-137`); the integration worker then performs its blocked-workspace check with that result (`apps/worker/src/integration/worker.ts:262-267`).
- **Concrete failure:** An event emitted before disconnect/purge, or a late callback from a stale fence, can reach the worker after the account row or integration mapping has changed. The job has no immutable workspace/account/fence to reject against; a lookup failure can become an unscoped retry or a fail-open path, while a reused integration identifier can route the event to the wrong current state.
- **Minimal plan amendment:** Carry immutable `workspaceId`, `accountId`, `inboxId`, `eventId`, `epoch`, and `fenceToken` in internal job metadata (or an equivalent signed route record). Before enqueue and before business effects, revalidate the current account/connection/fence; missing or purged scope must be a terminal stale drop, not a retry. Add tests for a late callback after disconnect, workspace purge, account replacement, and blocked-owner handling.

### 4. High — The lease key does not include workspace scope

- **Plan location:** `phase-05-fenced-gateway-transport.md:19-22`; `phase-07-direct-messaging.md:27-30`. The plan requires workspace/account/inbox routing and cross-scope rejection.
- **Evidence:** The current lease key is derived only from `kind:id` (`apps/zalo-account-gateway/src/runtime/account-lease-store.ts:33-34`), while the runtime command contains workspace scope separately (`apps/zalo-account-gateway/src/runtime/ports.ts:63-67`). Pool serialization is likewise keyed by runtime kind and ID (`apps/zalo-account-gateway/src/runtime/zalo-account-pool.ts:22-23`).
- **Concrete failure:** If a runtime ID is ever supplied from a non-global namespace, or a malformed/internal command pairs an ID with another workspace, two scopes contend for the same Redis lease. One workspace can observe another workspace’s owner/fence transition, or a stop/reconnect can revoke the wrong runtime. Global database IDs may currently reduce the probability, but the lease contract is relying on that incidental property rather than enforcing scope.
- **Minimal plan amendment:** Make the canonical route and lease key include `workspaceId`, `accountId`/runtime ID, and (where relevant) `inboxId`; verify the persisted owner’s scope before accepting a target or fence. Add a same-runtime-ID/different-workspace test and reject cross-scope commands before touching Redis or the provider.

### 5. High — Crash between business effects and stream acknowledgement can duplicate work

- **Plan location:** `phase-05-fenced-gateway-transport.md:26,39-40,68`; `phase-07-direct-messaging.md:30-31,42-43`.
- **Evidence:** Event-bus handlers run before `XACK` (`packages/event-bus/src/event-bus.ts:440-471`). The generic integration job has no event ID or idempotency field (`packages/worker-config/src/queues/integration/index.ts:132-139`), and the enqueue helper only uses a caller-supplied `jobId` (`packages/worker-config/src/queues/integration/index.ts:1683-1697`). Message dedupe is expected to use `sourceId`, but the message uniqueness key also includes `createdAt` (`apps/worker/src/integration/handlers/received-message.ts:1244-1246`; `packages/database/src/schema/message.ts:89-94`).
- **Concrete failure:** A worker can commit a message, automation trigger, or realtime effect and crash before `XACK`; reclaim repeats the event. If normalization chooses a new timestamp, `sourceId` does not by itself prevent a second row under the current unique key. “Stable provider IDs” in the envelope do not make the downstream queue or all side effects idempotent.
- **Minimal plan amendment:** Require a deterministic job ID derived from the immutable route and provider event ID, and require a durable business idempotency/unique boundary before side effects. Document the crash ordering (effect committed before ack) and prove duplicate delivery does not duplicate messages, automation, audience effects, or realtime events. If the existing schema cannot provide that boundary, stop and replan rather than relying on stream IDs.

### 6. High — Ambiguous outbound sends can duplicate after result expiry or restart

- **Plan location:** `phase-05-fenced-gateway-transport.md:23,27`; `phase-07-direct-messaging.md:30-31,42-43`; `plan.md:113` (no automatic retry for a non-idempotent send).
- **Evidence:** The reference provider returns provider message IDs only after `sendMessage` accepts the operation, and recommends a durable echo/client ID for reconciliation (`plans/261120-0350-zalo-account-channel-messaging/reports/zalocrm-reference.md:300-317,486-488`). The transport result is only a bounded-TTL correlation (`phase-05-fenced-gateway-transport.md:23`), so a crash before publishing the result can outlive the result record.
- **Concrete failure:** Zalo accepts a send, the gateway crashes before returning the provider ID, and the caller retries after the correlation TTL or on another owner. The second attempt is indistinguishable from a new send and produces a duplicate. A late echo may then arrive after the duplicate has already triggered automation.
- **Minimal plan amendment:** Persist an outbound intent/idempotency record before dispatch, reuse the same command/client ID across retries and restarts, and leave an `unknown` result terminal until an echo or explicit reconciliation proves the outcome. Never re-dispatch an unknown non-idempotent send merely because its result TTL expired. Add a crash-after-provider-acceptance/before-result test, including retry after restart and late echo.

### 7. High — Gateway shutdown has no bounded deadline or failure ordering

- **Plan location:** `phase-05-fenced-gateway-transport.md:52,68`; `plan.md:118`. The plan promises bounded reclaim/shutdown and a drain/ack rollback path but does not define the deadline or ordering.
- **Evidence:** SIGTERM awaits `server.close()`, sequential `pool.shutdown()`, and Redis quit with no timeout (`apps/zalo-account-gateway/src/main.ts:50-78`). Pool shutdown waits for each runtime in sequence (`apps/zalo-account-gateway/src/runtime/zalo-account-pool.ts:105-123`); runtime finish publishes `closed` before releasing the lease and can await the event sink (`apps/zalo-account-gateway/src/runtime/zalo-account-runtime.ts:411-447`). Detached errors are swallowed (`apps/zalo-account-gateway/src/runtime/zalo-account-runtime.ts:462-464`). The generic event-bus worker has a six-second drain, but the gateway is not tied to that bound (`packages/event-bus/src/worker.ts:7-47`).
- **Concrete failure:** A blocked provider upload, Redis operation, or sink call holds SIGTERM indefinitely. If the process is eventually killed, the lease is not explicitly revoked, an active listener can outlive the intended drain, and in-flight sends/events can be redelivered without a documented state. Conversely, publishing `closed` can fail while the provider listener remains active until the process exits.
- **Minimal plan amendment:** Define a shutdown state machine and hard deadline: stop accepting commands, pause consumers, atomically mark/revoke leases, stop provider listeners, drain only bounded in-flight work, then close Redis; force exit with an explicit metric if the deadline expires. Make late callbacks no-ops after the shutdown fence and log detached failures. Add tests with a hanging SDK call, hanging sink, Redis outage, and late provider callback.

### 8. High — Provider outages and rate limits can create a reconnect/sync thundering herd

- **Plan location:** `phase-05-fenced-gateway-transport.md:23,52`; `phase-06-channel-registration-and-inbox.md:18-24`; `phase-08-group-control.md:46-51`; `phase-09-native-labels-and-tags.md:47-53`.
- **Evidence:** The current reconnect breaker is per runtime and counts local closes (`apps/zalo-account-gateway/src/runtime/reconnect-policy.ts:15-27`); each runtime schedules its own reconnect (`apps/zalo-account-gateway/src/runtime/zalo-account-runtime.ts:317-353`). The provider report calls out unstable error categories, disconnected/closed phases, and unverified limits (`plans/261120-0350-zalo-account-channel-messaging/reports/zalocrm-reference.md:474-505`). There is no provider-wide admission budget in the plan.
- **Concrete failure:** A Zalo outage or rate limit makes many accounts reconnect, enumerate groups, or refresh full label documents independently. Jitter on each account is not a provider-wide circuit breaker. A rate-limit response can be misclassified as auth/transient, causing repeated requests or a non-idempotent send retry and worsening suspension risk.
- **Minimal plan amendment:** Define typed provider outcomes (`reauth`, `denied`, `rate_limited` with `Retry-After`, transient, and ambiguous), per-account plus provider-wide circuit/backoff/admission budgets, and a manual/operator reset. Pause group/label scans and non-idempotent sends while rate-limited; never automatically retry ambiguous sends. Add an outage/rate-limit burst test that verifies bounded provider calls and no duplicate sends.

### 9. High — Bounded stream length can silently discard lagging unacked work

- **Plan location:** `phase-05-fenced-gateway-transport.md:26,46-52,68`; `plan.md:100`. “Bounded retention” is required, but its relationship to maximum outage/lag is not defined.
- **Evidence:** The existing producer uses approximate `XADD MAXLEN` by entry count (`packages/event-bus/src/event-bus.ts:113-159`), not a byte/age budget. Consumers process batches of up to 500 (`packages/event-bus/src/event-bus.ts:203-226`), and acknowledged entries are not explicitly deleted (`packages/event-bus/src/event-bus.ts:228-230`). A stream can therefore trim old entries while a consumer is stalled or its PEL is being reclaimed; the plan does not state what happens when the stream entry behind a pending ID is gone.
- **Concrete failure:** During a provider outage, worker outage, or slow poison-entry loop, retention is reached and an unprocessed command/event disappears. Reclaim can see a pending ID without a payload, while the API may still report a started/accepted operation. The system loses a message without a durable DLQ record or an operator-visible gap.
- **Minimal plan amendment:** Set retention from a documented worst-case lag plus headroom, with both byte and age limits where possible; monitor oldest pending ID versus stream first ID and alarm before unsafe trimming. Define a gap policy (producer backpressure or durable overflow/DLQ) rather than silent loss, and add a recovery test that exceeds the retention window with pending entries.

### 10. High — Malformed/oversized stream entries can become permanent poison entries

- **Plan location:** `phase-05-fenced-gateway-transport.md:35-39,47,52,68`.
- **Evidence:** Stream payload parsing calls `JSON.parse` without per-entry recovery (`packages/event-bus/src/event-bus.ts:412-422`). Reclaim parses claimed entries before it checks delivery count (`packages/event-bus/src/event-bus.ts:523-562`); a parse exception exits the whole reclaim pass without `XACK` or DLQ placement. New-read parsing likewise occurs in the consume loop (`packages/event-bus/src/event-bus.ts:203-226`).
- **Concrete failure:** One truncated JSON value, unknown schema, secret-bearing oversized payload, or bad producer write is retried forever in the pending list. Each reclaim pass fails at the same entry, later entries are delayed, lag grows, and the configured max-delivery/DLQ policy never runs.
- **Minimal plan amendment:** Handle parse and schema errors per entry: increment its delivery count, write a redacted/bounded DLQ record with the reason and stream ID, then `XACK` the poison entry. Do not include raw secrets or unbounded payloads in the DLQ. Add malformed JSON, unknown kind, missing scope, and oversized-entry tests through restart/reclaim.

### 11. High — Group sync can mistake a partial provider snapshot for deletion

- **Plan location:** `phase-08-group-control.md:18-21,26,34-40,46,49`.
- **Evidence:** The provider returns group discovery as `gridVerMap`/`gridInfoMap`, with IDs taken from the version map and detail calls chunked in groups of 50 (`plans/261120-0350-zalo-account-channel-messaging/reports/zalocrm-reference.md:368-380`). The phase requires handling removal/inaccessibility but does not define snapshot completeness, sync generations, or a tombstone state.
- **Concrete failure:** A rate-limited or failed detail chunk, permission transition, malformed response, or partially populated version map looks like “not present.” A reconciliation that deletes or leaves `sendEnabled` true based on that partial view can either remove a valid group or retain a group that will repeatedly reject sends. A later healthy snapshot cannot reliably distinguish a real deletion from an incomplete run.
- **Minimal plan amendment:** Stage each sync with a `syncRunId`/generation and completeness status; only mark a group missing after all discovery/detail chunks succeed. Preserve a bounded tombstone/inaccessible state and disable sends while uncertain; retry failed chunks with a cap and never perform destructive deletion from a partial run. Add tests for missing chunk, rename, inaccessible group, and recovery on the next complete snapshot.

### 12. High — Label whole-document writes remain unsafe across crash and lease handoff

- **Plan location:** `phase-09-native-labels-and-tags.md:18-23,36-38,46-53,57`.
- **Evidence:** Zalo labels are a whole document with a provider version; writes can race, and provider reads can lag one to three seconds (`plans/261120-0350-zalo-account-channel-messaging/reports/zalocrm-reference.md:394-423`). The report notes that the reference serial queue is in-memory and not wired to the current provider. The phase relies on per-account serialization and response-seeded cache but does not require durable mutation state across process ownership changes.
- **Concrete failure:** Mutation A is accepted, but the gateway crashes before it records the response. A new owner reads a stale version, applies mutation B to an old full document, and overwrites A or an unrelated label change. An “uncertain” path that refreshes and writes without proving the provider version has the same lost-update risk.
- **Minimal plan amendment:** Persist a per-account mutation intent/version (or use an equivalent durable compare-and-reconcile record); after an ambiguous update, pause further writes until a fresh read proves the accepted version or an operator resolves it. Bound conflict retries and make the lease/fence part of the mutation record. Add crash/lease-handoff/provider-lag tests proving no lost labels.

### 13. High — Payload and lifecycle maps are not bounded enough for account churn

- **Plan location:** `phase-05-fenced-gateway-transport.md:46-52`; `phase-07-direct-messaging.md:56`; `phase-08-group-control.md:26`; `phase-09-native-labels-and-tags.md:57`.
- **Evidence:** The event bus serializes the entire payload and materializes batches concurrently (`packages/event-bus/src/event-bus.ts:113-159,203-226,299-393`); its `lastProcessingErrors` map retains entries while the PEL grows (`packages/event-bus/src/event-bus.ts:640-645`). QR events carry a data URL (`packages/sdk/src/lib/zalo-account.ts:38-43`). The gateway pool retains epoch/cancellation maps and runtime state in memory (`apps/zalo-account-gateway/src/runtime/zalo-account-pool.ts:25-31,131-179`), while provider label documents contain conversation arrays (`plans/261120-0350-zalo-account-channel-messaging/reports/zalocrm-reference.md:394-401`) and group discovery returns all groups in one object (`.../zalocrm-reference.md:368-380`).
- **Concrete failure:** A large label/group response, QR/media payload, or burst of stream entries is copied into Redis, JSON strings, parsed batches, and handler queues at once. Repeated connect-session churn leaves cancellation/epoch entries behind; failed entries can grow the error map with the PEL. The gateway can OOM despite commands being run sequentially and despite a nominal stream count cap.
- **Minimal plan amendment:** Set hard byte/item limits at schema and producer boundaries; reject/quarantine oversized entries with redacted metadata, and never put raw media/auth in ordinary streams. Bound per-account queues and active runtimes, page group/label work, evict completed runtime/error-map keys, and expose backpressure/PEL metrics. Add near-limit and churn/flood tests, including oversized QR/label/group payloads.

### 14. Medium — Health and logs can report availability while the transport is broken

- **Plan location:** `phase-05-fenced-gateway-transport.md:52`; `phase-09-native-labels-and-tags.md:53`; `plan.md:106`.
- **Evidence:** Detached runtime failures are silently discarded (`apps/zalo-account-gateway/src/runtime/zalo-account-runtime.ts:462-464`), and lease-renewal failures are caught without an error log (`apps/zalo-account-gateway/src/runtime/zalo-account-runtime.ts:170-183`). `/healthz` always returns 200 (`apps/zalo-account-gateway/src/server.ts:15-19`), while `/readyz` only reflects the local Redis-ready flag (`apps/zalo-account-gateway/src/main.ts:38-40`). Redis connection failure currently only emits a warning (`apps/zalo-account-gateway/src/main.ts:97-103`).
- **Concrete failure:** Operators see a healthy process even when command/event consumers are stopped, a lease is repeatedly lost, sink publication is failing, or pending entries/DLQ are growing. Silent detached errors make an account appear connected in the UI while no inbound event reaches the worker; there is no alertable distinction between provider silence and transport lag.
- **Minimal plan amendment:** Make readiness require Redis plus active command/event consumers and a measured lease/stream heartbeat. Add structured, redacted counters/gauges and alert thresholds for accepted/rejected/stale/timeout/ambiguous commands, event append rejection, lease renewal/fence loss, stream lag/PEL/reclaim/DLQ/poison, provider error category/rate limit, group-sync completeness, and label conflicts. Log detached failures with scoped IDs but never auth, cookies, QR, or message content. Add failure-to-metric tests.

### 15. Medium — Migration rollback and purge compatibility is not operationally drilled

- **Plan location:** `plan.md:63-69,116-124`; `phase-06-channel-registration-and-inbox.md:46,64,73`; `phase-08-group-control.md:30,45-51,69-73`.
- **Evidence:** Workspace disconnect/purge has no Zalo Account branch yet (`packages/business/src/workspace-lifecycle/service.ts:708-898`), the `InboxWithIntegrations` type omits the account relation (`packages/database/src/types.ts:314-326`), and purge registration is an explicit table list with no group table today (`packages/database/src/repositories/workspace-purge/tables.ts:1-31,82-141`). The plan’s rollback is feature-gating and stopping runtimes, not a mixed-version or partial-DDL drill.
- **Concrete failure:** A new worker/gateway cohort assumes the group table or relation before all instances have the migration, or an old cohort receives new commands after a rollback. Disabling the gate without stopping/revoking runtimes can leave live provider sessions after rows are deleted; if the new group table is not registered in bounded purge, workspace deletion leaves orphaned group rows or retains sensitive metadata. A failed/partially applied DDL can strand a mixed deployment.
- **Minimal plan amendment:** Add a compatibility matrix and rollout/rollback drill: add-only migration and index verification first; code must tolerate the pre-migration schema behind the gate; disable producers/consumers/UI before stopping and revoking runtimes; retain rows rather than down-migrating. Register group/account rows in bounded purge with stop/revoke-before-mutation ordering, and test partial migration, old/new worker coexistence, rollback, and workspace purge.

## Operational gaps to close before accepting items 5–9

The plan already calls for fences, stable IDs, bounded retention, and redacted metrics. The failure cases above show where those words need an executable boundary: fan-out topology, startup reconciliation, immutable route scope, durable idempotency for both inbound and outbound paths, bounded shutdown, provider-wide admission control, complete-sync/tombstone semantics, durable whole-document label conflict handling, per-entry poison handling, hard payload limits, and readiness/alert signals. These can be added as focused RED tests and acceptance criteria without parallel commands or relaxing the sequential low-RAM gate.
